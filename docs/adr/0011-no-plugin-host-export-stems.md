# 0011 不做插件宿主，改导出分轨给外部 DAW

- 日期：2026-11-13
- 状态：已决定（M10-T15 的结论）
- 相关：`timeline::export::stems`、`app::stems`、`timeline::mixer`

## 背景

M10-T15 的问题只有一个：要不要做 VST3 / AU 宿主，让用户能在时间线上挂第三方音频插件
（降噪、混响、母带）。

「做」意味着三件事同时成立：

1. **三套 ABI**：VST3 的 C++ 接口在三个平台各有编译器 / 运行时差异（MSVC 与 clang 的
   `std::string` 布局、macOS 上 AU 是另一套 API），Rust 侧要么绑 `vst3-sys` 之类的
   绑定、要么自己写薄壳，两边都得跟上游版本对齐。
2. **崩溃隔离**：插件是第三方二进制，崩起来是整个进程一起没。要隔离就得把插件放进
   独立进程、音频样本走共享内存来回搬，还要处理插件窗口的托管（插件自己创建
   `NSView` / `HWND`，得嵌进 GPUI 的窗口里）。
3. **参数与状态的持久化**：每个插件的参数表、预设、自动化目标都要进工程文件，还要
   跟着撤销栈走。

这三件都不是「加一个面板」的量级——按同类项目（Shotcut 的 MLT、Kdenlive）的经验，
一个能用的宿主是数人年。

## 决策

**不做 VST3 / AU 宿主。** 需要的插件处理走「导出分轨 → 外部 DAW 处理 → 回导素材」。
M10-T15 从路线图移除。

同时把替代路径做实：`编辑 > 导出音频分轨…`（`timeline::export::stems`）把每条听得见的
音频轨各写成一个 24bit / 48kHz 立体声 wav，文件名 `01-轨名.wav`、长度一律等于序列长度，
推子 / 自动化 / 声像 / 速度曲线都已经算在里面。

## 理由

- **这不是一个混音工作站**。项目目标是「从零编排成片」（见 TODO.md 与 `AGENTS.md`），
  混音能力只需要「三条轨各自推一下、压一条曲线」——`timeline::mixer` 的三层音量
  （片段 → 自动化 → 推子）加等功率声像已经覆盖。真正需要插件的是**精修**，那一步
  用户本来就更愿意在熟悉的 DAW 里做。
- **分轨的代价只有一次往返**。wav 是通用格式，任何 DAW 都认；序列长度对齐让回导之后
  直接放在原时间位置，不用重新对轴。相比之下宿主方案要在本程序里重造一套「插件扫描 +
  参数自动化 + 延迟补偿」，收益只是省去一次导出。
- **崩溃隔离的成本远高于收益**。进程外宿主等于再写一套 IPC 音频通道；进程内宿主则是
  「一个空指针插件就能让用户的工程一起崩」。两种都不划算。
- **未来要接插件，入口还在**。真需要的时候，最小可行形态是「单轨离线处理」：导出这一轨
  → 用插件渲染 → 回导，与本 ADR 的替代路径是同一条链，只是自动化了中间那一步。

## 代价

- 用户要在两个程序之间来回：处理完的分轨要么回导成素材铺回时间线，要么在 DAW 里直接
  出成片。
- 分轨导出没有进度条、不可取消（一条分轨几秒到几十秒，弹横幅说「2/3」）。真要做，
  按 `render_cache_queue` 的样子加一个队列状态即可。
- 分轨不带视频参考。需要「按画面卡点」的混音要自己在两个窗口间对时间码。

## 未选的方案

- **进程内 VST3 宿主**：崩溃即工程丢失，得先做工程快照 + 恢复，等于把隔离问题推给
  另一种形式的补丁。
- **进程外宿主（独立音频进程 + 共享内存）**：技术上最干净，但要维护一套 IPC 音频通道
  与插件窗口重定向，短期不划算。
- **只支持 AU（macOS 优先）**：与「一套纯 Rust 代码、三个平台同源」的项目前提冲突。
- **接入 LV2 / CLAP**：CLAP 的 C ABI 确实比 VST3 友好，但同样需要隔离、参数持久化与
  窗口托管；不做的结论与 API 选择无关，所以也不列为首选替代。

## 复评条件

满足其中任意一条，就把这件事重新拿出来评估：

1. 用户需求集中在「一两个固定插件」（例如只用某个降噪），那时值得做「单轨离线处理」
   的窄接口，而不是通用宿主。
2. 导出分轨的往返被证明是主要痛点（例如有工程需要反复迭代混音）。
3. 出现成熟的、跨平台的、进程外隔离的 Rust 音频插件宿主库，直接用比自己写便宜。
