# 0008 预览改用多路合成，单路 mpv 只留作回退

## 状态

提议（尚未实现）。目标上取代 M4-T02「预览只解一路」的限制；与 0007 的色彩管理不冲突。

## 背景

现在的预览是「一个 mpv 实例 + 按序列时间 seek」：换素材才 `Load`，其余靠 seek 追。
这条路径已经能连续播一条单轨时间线，但有两个天花板：

1. **只有一路画面。** 多轨叠加、画中画、遮罩、混合模式在预览里不存在，用户只能导出
   之后才知道叠出来是什么样。
2. **没有合成就没有实时反馈。** 转场、效果栈、关键帧都只能「先导出再看」，而专业剪辑
   的第一需求是「改一下立刻看到」。

导出侧已经能用 ffmpeg 做 `overlay` / `xfade` / 滤镜链，但那是离线一次算完。要在播放时
看到同样的结果，必须自己完成「多路解码 → 合成 → 呈现」，或者把这条计算交给一个能
实时跑的图。

现有渲染路径（`player/engine/render_loop`）是 `MPV_RENDER_API_TYPE_SW`：mpv 把帧渲染到
一块 CPU 内存，再作为 `RenderImage` 推给 GPUI。这条路径跨平台一致、没有 GL/wgpu 互操作，
代价是每帧多一次 1080p 约 8MB 的拷贝，并且只在单路上验证过。

## 候选方案

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A 多实例 + CPU 合成 | 每条视频轨一个 mpv，SW 渲染到内存，CPU 做缩放 / alpha / 混合 | 不改现有渲染路径，三平台一致，风险最低 | 1080p 两路尚可，4K 或三层必掉帧；每帧多次全画面拷贝 |
| B 多实例 + GPU 合成 | 每条轨一个 mpv，经 D3D11 / OpenGL 出纹理，交换到 wgpu 由 GPU 合成 | 能实时，可扩展效果与转场 | 三平台三套互操作；显存与设备丢失；现有 SW 路径要并行保留 |
| C 单实例 + lavfi | 一个 mpv，用 `--lavfi-complex` 描述整条时间线 | 不用自己合成，滤镜全在 mpv 内 | 图一变就要重载，交互剪辑下等于卡死；时间线到 lavfi 的映射很脆 |
| D 预渲染代理 | 后台按块渲染小尺寸代理，播放时顺序播 | 不改解码架构，复杂时间线也能播 | 不是实时；改一处要重渲一块；只能作为补充 |

## 决定

1. **目标架构是 B，但按 A → B 两步落地**：
   - 第一步（`M10-T01`）用 A 做两路合成，验证「多路解码 + 合成语义 + 与导出一致」；
   - 第二步（`M10-T02`）在 Windows 上先做 B（D3D11 → wgpu），macOS / Linux 后补。
2. **A 永久保留为回退**：GPU 初始化失败、设备丢失、远程桌面、老显卡时退回 A，再不行
   退回现在的单路路径。降级链是 `B → A → 单路`，每一级都在界面上说明原因，不静默降级。
3. **单轨、单素材的序列仍走现有单路路径。** 合成器只在「需要两路以上」或「有转场 /
   效果 / 关键帧」时接管，避免为简单时间线付出多实例的启动与内存代价。
4. **音频不进合成器。** 每条音频轨一个 `--no-video` 的 mpv 实例，交给系统混音器混合
   （WASAPI 共享 / CoreAudio / PulseAudio）；同步靠统一起点 + 周期校正，目标误差
   < 40ms。理由：自研音频引擎（重采样、时钟、设备切换、独占模式）的成本远高于收益，
   而多实例在三个平台上都能直接工作。
5. **拒绝 C**：交互剪辑的第一需求是「改一下立刻看到」，lavfi 图重建的延迟不可接受；
   它更适合批处理，不适合预览。
6. **D 独立推进**（`M10-T19`），不替代 B：缓存用来兜住「B 也跑不动」的复杂时间线，
   而不是取代实时。

## 后果

- 线程模型不变：解码与合成在后台线程，结果经 `futures::mpsc` 推给主线程；`AsyncApp`
  不是 `Send` 这条约束继续成立。
- `player/engine` 要能把「一帧」从「一个 mpv 的输出」变成「合成结果」，截图、示波器、
  悬停缩略图都改为从合成结果取（`M10-T03`），否则它们会拿到错的画面。
- 预览与导出仍是两条实现，但必须共用同一份「时间线 → 图层 / 转场 / 关键帧」的描述
  （`timeline::preview` 已经这样处理选轨规则）。一致性靠 `M10-T01` 的对比测试守。
- 多实例意味着内存与句柄成倍增长：每路 mpv 都有解码缓冲与 demuxer 线程。上限设为
  「同时活跃视频轨 ≤ 4」，超出的轨道按可见性降级为缓存帧。
- 转场在预览里由合成器做（alpha 混合 / 位移），导出仍用 `xfade`。两者不可能逐像素
  相同，验收标准是「同一时刻构图与透明度一致」，不是像素相等。
- 单文件分发的体积不变（libmpv 已经在内嵌里），但运行时内存基线会从「一个实例」
  涨到「一路实例」，需要在 README「已知限制」里写明。

## 未决问题

- 合成在哪个色彩空间做：bt709 还是线性？线性更正确，但每帧多两次转换。
- HDR 预览：现在统一转 SDR 后再合成（见 0007）。若将来做 HDR 工程，合成器要改。
- macOS 是等 mpv 的 Metal 渲染，还是走 OpenGL → wgpu 的桥。
- 超过 4 路的时间线是否直接放弃实时，强制走渲染缓存。
