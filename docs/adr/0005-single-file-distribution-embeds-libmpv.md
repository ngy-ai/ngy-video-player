# 单文件分发：把 libmpv 内嵌进可执行文件

release 构建由 `build.rs` 把 `libs/<平台>/` 下的 libmpv 写进二进制，运行时解压到
用户缓存目录再交给动态加载器（`src/player/embed.rs`）。debug 构建、以及
`NGY_EMBED_MPV=0` 的构建不这么做。

起因是一个反复出现的失败：`cargo build --release` 之后把 `target/release` 里的 exe
单独拷出去，程序报「找不到可用的 libmpv」。库一直在 `libs/` 里，但那个目录只在开发
树里成立；「拷一个 exe 走」是分发时最自然的动作，也恰好把库丢掉了。

曾考虑的替代做法是随包附带 dll（一个 zip 里放 exe + dll，`bundle-macos.sh` 的
`.app` 就是这个形态）。它体积小、启动快，但把「dll 要摆对位置」这个构建细节变成
用户的操作负担，而上面那个失败正是用户在不知情的情况下踩中的。内嵌把这件事收进
构建：产物是什么样，运行就是什么样。

代价是明确的：exe 从 10MB 涨到约 130MB（库本身 116MB），首次启动多一次解压
（约一秒，之后走缓存）。所以它只挂在 release 上——开发期 `libs/` 就在手边，
每次链接都搬运上百 MB 没有意义。

不变的部分：

- 仍然是**运行期**加载，不链接、不需要头文件与 C 工具链；
- 磁盘上已有的库优先于内嵌的那份，用户特意换过的版本不该被内置的旧库盖掉；
- 解压失败、缓存目录不可写时，照旧走「窗口能打开、界面里写明缺什么」的路径，
  不会启动即崩。
