# 小窗是工具窗口，不进任务栏与 Alt+Tab

小窗用 `WindowKind::PopUp` 创建，在 Windows 上落到 `WS_EX_TOOLWINDOW | WS_EX_TOPMOST`：任务栏和 Alt+Tab 里都看不到它。

选它的理由是小窗模式的定义——同一时刻只有主窗口或小窗之一可见。如果小窗是普通窗口，任务栏会同时出现「最小化的主窗口」和「小窗」两条同一个应用的记录，点哪一条都会变得含糊；只留主窗口那一条，「点任务栏等于回到小窗」才有唯一解。

代价是这条路径在 Windows 上没有 `WS_THICKFRAME`，gpui 自绘的缩放边框只在窗口上边缘生效，左右下三条边拖不动。小窗的尺寸本来就写进首选项、且高度按画面比例锁定，四边缩放并非必需能力——但这不代表它是免费的，不要当成 bug 去「修」。

创建时带的 `WS_EX_TOPMOST` 只是初始值：悬浮条上的图钉可以把它摘掉（`SetWindowPos(HWND_NOTOPMOST)`），状态存进 `mini_on_top`，下次开小窗照它恢复。

**任务栏属性不跟着图钉走**：工具窗口这一条对置顶与否都成立。曾经让「取消置顶」顺手把 `WS_EX_TOOLWINDOW` 换成 `WS_EX_APPWINDOW`，好让被盖住的小窗能在任务栏找回来——但那会让任务栏同时出现主窗口和小窗两条，一眼看去像开了两个播放器，比「找不回来」更难接受。

所以取消置顶的语义就是老老实实的「不再压住别的应用」，但**在普通窗口这一层里它应当是最前的**：点小窗任意位置都会 `SetWindowPos(HWND_TOP)` 抬一次（`platform::topmost::raise`），只被置顶窗口压住。只靠系统默认的点击激活不够确定——被盖住时激活并不总会把它抬到那一层的最前。

如果被完全盖住，点任务栏里本程序那一条（最小化的主窗口）就是那条退路。系统的还原只针对主窗口，所以它必然先可见一会儿：可见性观察者当场把它同步最小化回去（`platform::window::minimize`，不能用异步的 `minimize_window`，否则主窗口会实打实闪一帧），再用 `platform::window::bring_to_front` 把小窗抬到前台、把前台权抢回来。

系统也可能反过来对「整个应用」下手：主窗口本来就最小化着，被收走的只有小窗，点任务栏反而成了关掉播放器的开关。所以小窗自己盯着自己的可见性，被收起就 `activate_window` 召回（`MiniPlayer::recall`）。两条合起来，点任务栏的结果恒定为「还是小窗」。

中间的还原动画是这条路径的代价：Win32 没给普通窗口留「拒绝被还原」的口子，只能事后纠正。真正退出小窗的入口只有小窗悬浮条上的还原按钮，以及小窗里的 Esc / T。
